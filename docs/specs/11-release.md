# Project Spec: Phase 11: Release

## 1. Overview and Goal
* **Purpose:** Ship PhotonForge v1.0 as installable packages for Windows, Linux, and macOS,
  with user documentation, a safety guide, and a contributor workflow.
* **Success Criteria:**
  * A tag push (`v*`) builds and attaches artifacts to a GitHub Release automatically: Windows `.msi` + `.zip`, Linux `.AppImage` + `.tar.gz`, macOS `.dmg` (universal or per-arch).
  * Fresh installs on each OS launch and complete the M2 workflow (import → export) without extra setup.
  * User docs cover installation, first-run machine setup, GRBL configuration, and laser safety.
  * `CHANGELOG.md` and `CONTRIBUTING.md` exist and are linked from the README.

## 2. Tech Stack and Architecture
* **CI:** GitHub Actions release workflow, triggered on `v*` tags.
* **Packaging tools (⚠️ approve; these are build tools, not crate dependencies):**
  * Windows: `cargo-wix` (MSI).
  * Linux: `linuxdeploy` / `appimagetool`.
  * macOS: `cargo-bundle` plus `hdiutil` (DMG). Signing/notarization is optional and needs an Apple Developer account (your decision).
* **Versioning:** SemVer. The workspace `version` is the single source of truth, and the git tag matches it.
* **Docs:** Markdown in `docs/user/`. Publishing to a site (mdBook or GitHub Pages) is optional and needs approval.

## 3. Executable Commands
* **Release build:** `cargo build -p pf-app --release`
* **Windows MSI:** `cargo wix -p pf-app`
* **macOS bundle:** `cargo bundle -p pf-app --release`
* **Full pre-release check:** `cargo fmt --all -- --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`
* **Tag a release:** `git tag v1.0.0 && git push origin v1.0.0`

## 4. Project Structure
* `.github/workflows/release.yml`: build matrix, packaging, release upload.
* `crates/pf-app/wix/main.wxs`: MSI definition (generated by `cargo wix init`).
* `packaging/linux/photonforge.desktop`, `packaging/linux/photonforge.png`: AppImage metadata.
* `packaging/macos/Info.plist`: bundle metadata (if `cargo-bundle` metadata isn't enough).
* `docs/user/installation.md`, `first-run.md`, `grbl-setup.md`, `safety.md`.
* `CHANGELOG.md` ([Keep a Changelog](https://keepachangelog.com) format), `CONTRIBUTING.md`.

## 5. Code Style and Conventions
* `CHANGELOG.md` entries are grouped under `Added`, `Changed`, `Fixed`, `Safety`. Safety-relevant changes are always called out.
* The GRBL setup docs cite the GRBL wiki for every `$` setting:
  ```markdown
  ### `$32` – Laser mode
  Must be `1`. In laser mode GRBL turns the laser off during G0 rapids and
  keeps moving through power changes without stopping. *(GRBL v1.1 laser_mode.md)*
  ```
* The release workflow pins every action to a version (`@v4`, never `@main`).

## 6. Boundaries and Guardrails
* **Always do:** Run the full pre-release check and the hardware checklist (`docs/hardware-test.md`) before tagging. Include the GPL-3.0 license and source link in every package.
* **Ask first:** Before choosing code signing, publishing a website, adding telemetry or auto-update (both off by default if ever added), and before tagging any release.
* **Never do:** Never ship a build with relaxed safety defaults. Never bundle third-party fonts or assets without verifying a GPL-compatible license. Never modify `LICENSE`.

## 7. Implementation Phases
* **11.1 Release builds:** a release profile (`lto = "thin"`, `codegen-units = 1`, `strip = true`). Verify a binary on each OS.
* **11.2 Windows packaging:** `cargo-wix`, MSI + zip in CI.
* **11.3 Linux packaging:** AppImage + tar.gz in CI.
* **11.4 macOS packaging:** `.app` + DMG in CI (signing per your decision).
* **11.5 Release workflow:** a tag-triggered pipeline that uploads to GitHub Releases.
* **11.6 User docs:** installation, first run, GRBL setup, safety.
* **11.7 Project docs:** CHANGELOG, CONTRIBUTING, README polish.
* **11.8 v1.0.0 release (⚠️ approval):** final checks, then the tag.
